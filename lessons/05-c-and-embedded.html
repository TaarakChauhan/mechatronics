Module 5 — Embedded brains

C and embedded software

C remains the lingua franca of bare-metal and RTOS embedded systems: close to the machine, portable enough, and supported by every toolchain.

Why C

Predictable data layout, volatile-qualified register access, and mature compilers make C a fit for drivers and control loops. C++ is common too (with discipline). Garbage-collected languages appear on SBCs, not usually in the innermost 10 kHz current loop.

Structure and I/O

Typical firmware: init clocks/pins → init peripherals → enable interrupts → super-loop or RTOS tasks. Hardware abstraction layers (HAL) wrap registers. Serial comms (UART) print diagnostics; SPI/I²C talk to sensors; CAN/Ethernet talk to the machine network.

/* Original teaching sketch — blink + read button (Arduino-class style) */
const int LED = 13;
const int BTN = 2;
void setup() {
  pinMode(LED, OUTPUT);
  pinMode(BTN, INPUT_PULLUP);
  Serial.begin(115200);
}
void loop() {
  bool pressed = digitalRead(BTN) == LOW;
  digitalWrite(LED, pressed ? HIGH : LOW);
  Serial.println(pressed ? "RUN" : "IDLE");
  delay(50);
}

Worked example — discrete P control in C

float kp = 2.5f;
float setpoint = 1.0f; /* volts equivalent */
float y = read_adc_scaled();
float u = kp * (setpoint - y);
if (u < 0) u = 0; if (u > 1) u = 1;
write_pwm_duty(u);

This is not production code (no timing, filtering, or fault checks) but shows the mapping from control law to embedded C.

Watch-out Busy-loop delay() blocks further work. Prefer timers and state machines as systems grow.

Key terms

HAL
Hardware abstraction layer.
volatile
C qualifier preventing unwanted optimisation of hardware-mapped objects.
RTOS
Real-time operating system providing tasks and scheduling.

Concurrency patterns

Beyond the Arduino loop, production firmware uses timer interrupts for sampling, DMA for ADC buffers, and an RTOS for communications stacks. Shared variables between ISRs and tasks need atomic access or queues. Heisenbugs that vanish when you print are classic signs of missing volatile/atomicity or stack overflow.

Coding standards (MISRA-style discipline, static analysis) exist because undefined behaviour in C becomes unpredictable actuators. Treat warnings as defects in safety-related code.

Numerical care in control code

Use fixed-point or carefully scaled integers on small MCUs when floating point is soft and slow; document scaling. On Cortex-M4F and above, float PID is often fine if you still mind NaNs from sensor faults.

Never divide by a sensor-derived quantity without checking zero. Guard every normalisation.

Keep ISRs short: queue flags, push data to queues, exit. Long ISRs raise latency for other edges and create priority chaos.

Version-stamp firmware in a queryable register or string so field technicians can report exactly what runs — a communications-and-faults practice implemented in software.

Extended studio notes — 05 c and embedded

In professional mechatronics work, the ideas in this lesson show up less as isolated definitions and more as constraints that fight each other. Undefined behaviour in C becomes undefined actuator motion. When you write requirements, force numbers onto those constraints: sample rates, newton-metres, degrees Celsius, milliseconds of latency, millimetres of error. Vague adjectives hide trade-offs until tooling steel is already ordered.

A useful studio habit is to keep a living “assumption list” beside your block diagram. Typical assumptions include linearity, constant temperature, perfect sampling clocks, infinite actuator authority, and noise-free sensors. Assuming floating-point is free on every MCU surprises schedule on Cortex-M0. Crossing out an assumption should trigger either a model upgrade, a hardware change, or an explicit residual risk acceptance signed by someone accountable.

Commissioning is where theory meets cable trays. Expect ground loops, mis-labelled I/O, incorrect engineering-unit scales, and mechanical binding that looks like a “software bug.” Blocking delays in communications callbacks create priority inversion symptoms. Bring an oscilloscope or drive trace tool early; bring a torque wrench and alignment dial indicator just as early. The mechatronic engineer who only debugs in an IDE will misclassify half of field faults.

Documentation is part of the control system. Record firmware hashes, gain sets, mechanical revisions, and network topologies together. Future failure analysis needs that bundle. Structured error codes beat Boolean “fail” for field support. If your organisation treats documents as after-the-fact paperwork, expect to rediscover tuning constants from scratch after every staff rotation.

Finally, connect this lesson forward and backward in the course. Foundations without modern networks leave you unable to ship connected machines; modern buzzwords without foundations leave you unable to stabilise a simple loop. ROS 2 nodes later should still honour the same timing humility for bridges. Use the quizzes not as memorisation theatre but as prompts to redraw the diagrams from memory on paper — that retrieval practice builds the intuition you will need on a noisy factory floor.

Additional worked scenario

Discrete PID at Ts=0.01 s, Ki=2.0: integral gain per step adds 0.02*e. After 5 s of constant e=1 with saturation ignored, integral term is 10 — enough to slam the actuator when the error finally flips. Anti-windup clamping is mandatory, not optional polish.
